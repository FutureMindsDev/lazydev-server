# Serena End-to-End Test Plan

This document outlines the systematic testing procedure to verify that the `lazy-issue-resolver` NestJS application properly orchestrates the `serena-agent` Docker sidecar, injects Serena Memories, and successfully executes AST-level patches.

## Prerequisites
1. Docker Desktop must be running.
2. The `lazy-issue-resolver` network and volume dependencies must be present.

---

## 1. Infrastructure Validation
**Goal:** Verify the `lazydev-serena` container starts correctly and exposes the MCP SSE endpoint.

**Steps:**
1. Run `docker compose up -d serena` in the project's root directory.
2. Check container logs: `docker logs lazydev-serena`.
   - **Expected Output:** Logs indicating the FastMCP server started successfully and is listening on port `3333` over the `sse` transport.
3. Check the host connection to Serena: `curl -I http://localhost:3333/sse`
   - **Expected Output:** An HTTP response (e.g., `200 OK` or `405 Method Not Allowed`, indicating the server is responsive).

## 2. Codebase Integration Validation (NestJS)
**Goal:** Verify `SerenaMcpService` successfully connects to Serena using `StreamableHTTPClientTransport`.

**Steps:**
1. Start the NestJS backend: `npm run start:dev` (or via `docker compose up app`).
2. Observe the application boot logs.
   - **Expected Output:** 
     ```
     [SerenaMcpService] Initializing Serena MCP Client via SSE...
     [SerenaMcpService] Successfully connected to Serena MCP Server
     ```

## 3. Memories & RAG Injection Validation (`ResearchAgent`)
**Goal:** Verify the `ResearchAgent` correctly extracts project memory and merges it with the context.

**Steps:**
1. Create a dummy memory file inside a test repository workspace (e.g., `/app/worktrees/test-repo/.serena/memories/memory_maintenance.md`):
   ```markdown
   # Testing Memory
   Always use strict typing.
   ```
2. Dispatch a dummy payload to the Research Agent for `test-repo`.
3. Check the NestJS logs.
   - **Expected Output:**
     ```
     [ResearchAgent] Fetching core memories for /app/worktrees/test-repo...
     [SerenaMcpService] Calling MCP tool: read_memory...
     [ResearchAgent] Embedding query for vector search...
     ```
4. Verify the LLM context prompt generated by `ResearchAgent` contains the string: `--- Global Project Conventions & Memories ---` and the strict typing rule.

## 4. AST Patching Validation (`PatchGeneratorAgent`)
**Goal:** Verify Serena's `replace_symbol_body` tool accurately patches specific nodes in the tree without touching adjacent code.

**Steps:**
1. Use an intentional dummy response in the LLM service or mock the Langchain response with the following format:
   ```markdown
   ### SYMBOL: src/app.service.ts|AppService
   ```typescript
   export class AppService {
     getHello(): string {
       return 'Hello from Serena!';
     }
   }
   ```
2. Trigger the `PatchGeneratorAgent`.
3. Check the NestJS logs for:
   - **Expected Output:**
     ```
     [SerenaMcpService] Calling MCP tool: replace_symbol_body with args...
     [PatchGeneratorAgent] Patched symbol: AppService in src/app.service.ts
     ```
4. Inspect the resulting `src/app.service.ts` file in the worktree.
   - **Expected Output:** The class `AppService` is correctly updated, and file formatting/imports remain entirely intact.

## 5. Automated Unit Tests
**Goal:** Ensure recent deprecation cleanups and transport upgrades don't cause regressions.

**Steps:**
1. Run `npm run test`
   - **Expected Output:** All suites (including `embedding.service.spec.ts` and `vector-db.service.spec.ts`) pass, with zero unresolved dependencies (i.e. no missing `ast.service` modules).
